# ADR-0054: v1.0 public API freeze

- **Status**: accepted
- **Date**: 2026-05-30

## Context

Bead pf-gx3g is the API stability review that precedes the v1.0 tag.
Once 1.0 ships, the public surface is under semver: additive changes
only until 2.0. This ADR is the review's output. It enumerates the
frozen surface, records the conventions that shape it, and states the
decision to lock the surface as it stands rather than reshape it before
the tag.

The review found the surface already consistent. Every kernel follows
one return convention, the two precision profiles share a method
vocabulary, and there are no accidental exposures: no `#[doc(hidden)]`
items, no `#[deprecated]` items, and every public type carries private
fields reached only through methods and the read-only `Parts` view. The
review therefore recommends no pre-tag reshaping. The two changes the
tag ceremony (slice 8c) still makes are the version bump
`0.1.0` -> `1.0.0` and the crate-root doc, which today says the surface
is unstable.

One audit note recorded and dismissed: an earlier pass flagged an "exp
underflow defect" as a live blocker. It is not. The comment it read
(`src/math/exp.rs`) documents that slice p1.2 closed that defect and
turned the underflow stress block into a regression guard; `exp` is
correctly rounded (`tests/oracle/status/exp.toml`, `worst_ulp = 0`).

## Decision

Freeze the public surface as it stands at this commit. The version bump
to 1.0.0 lands at slice 8c.

### The frozen surface, by feature

- **Always:** `Sign`, `Status`.
- **`std`:** `flags` (the thread-local sticky-flag accessors).
- **`big`:** `BigFloat`, `BuildError`, `Parts<'a>`, `IeeeClass`,
  `ParseError`, `RoundingMode`.
- **`big` + `fixed`:** `FixedFloat<const PREC: u32>`,
  `ClassFixed<const PREC>`.

The arithmetic, transcendental, and special-function surface is exposed
as inherent methods on `BigFloat` and `FixedFloat<PREC>`, gated by the
kernel features (`ops`, `exp-log`, `trig`, `specials`, `agm`,
`integrals`, `airy`, `bessel`, `zeta`). The internal `ops/` and `math/`
modules are private; only the methods are public.

### Outside the v1.0 stability guarantee

The `ziv_instrumented` module is public only under the `ziv-instrumented`
feature (or `test`), and it re-exports internal Ziv calibration
constants and the trace type for the cross-check harness (ADR-0039). It
is an instrumentation hook, off in production builds, and is explicitly
**not** covered by the semver guarantee; its contents may change with
the internal Ziv driver. The same exclusion applies to everything
behind the `differential-mpfr`, `differential-arb`, and `kani`
features, and to the nightly toolchain pin (ADR-0011): the crate
requires nightly for `generic_const_exprs`, so the MSRV is the pinned
nightly in `rust-toolchain.toml`, not a stable release.

### Type properties (locked)

- All public types derive `Clone`, `Debug`, `Eq`, `PartialEq`, `Hash`;
  the fixed-size and attribute types (`FixedFloat`, `RoundingMode`,
  `Status`, `Sign`, `IeeeClass`, `Parts`, `ClassFixed`, `BuildError`,
  `ParseError`) are also `Copy`. `BigFloat` is not `Copy` (heap
  mantissa). `RoundingMode`, `Status`, and `Sign` derive `Default`.
- Fields are private throughout. Values are constructed through the
  `try_new_*` / `try_from_*` constructors and read through accessor
  methods and the `Parts` / `ClassFixed` views.
- All public enums are **exhaustive** (no `#[non_exhaustive]`). See the
  rationale below.

### Method conventions (locked)

- Every rounding operation takes an explicit `mode: RoundingMode` and
  returns `(value, Status)`, so callers inspect or accumulate IEEE
  754-2019 sticky flags without thread-local state. There is no hidden
  default rounding on the method surface; the `ops` feature's operator
  overloads are the one place `NearestEven` is implied, opt-in and
  documented (ADR-0007).
- Each arithmetic kernel carries four forms: the base
  `op(.., mode) -> (Self, Status)`, `op_round(.., precision, mode)` for
  an explicit output precision, and `op_with_flags` / `op_round_with_flags`
  that accumulate into a caller-supplied flag set for `no_std` use.
- Deliberate deviations from the `(value, Status)` shape, all locked:
  `partial_cmp` returns `(Option<Ordering>, Status)` (NaN ordering plus
  the signaling-NaN flag); `min` / `max` return `(Self, Status)` (IEEE
  minimum/maximum semantics); `parse_str` returns
  `Result<(Self, Status), ParseError>`; `to_decimal_string` returns
  `String`; `Display` formats under `NearestEven`.

### Intentional inconsistencies (reviewed, kept)

- **`_round` argument order.** The precision argument sits between the
  operands and the mode: `op_round(operand, precision, mode)`. Operands
  first, then modifiers; consistent across all kernels. Kept, not
  reordered.
- **Constructor divergence.** `FixedFloat` constructors omit precision
  (it lives in the type); `BigFloat` constructors take it explicitly.
  This is the dual-API design of ADR-0003.
- **`in_` suffix.** The modified Bessel `I_n` method is `in_` because
  `in` is a Rust keyword. Unavoidable; called out in the release notes.

### Why the enums stay exhaustive

`RoundingMode`, `Sign`, and `IeeeClass` mirror closed sets fixed by IEEE
754-2019; they will not grow within the v1.x line, and exhaustiveness
lets callers `match` without a catch-all arm. `BuildError` and
`ParseError` are small and stable. Marking any of these
`#[non_exhaustive]` would impose a catch-all arm on every consumer for a
growth that is not anticipated. The cost of being wrong is a single
2.0-gated breaking change, which is acceptable. Revisiting
`#[non_exhaustive]` (in particular for the error enums, should a new
failure mode appear) is recorded here as a deliberate post-1.0 question,
not an oversight.

### Documentation

`#![deny(missing_docs)]` is not enabled. The surface is documented in
practice (`cargo doc` renders the types and methods), but the lint is
not turned on for v1.0; enabling it is a separate, additive hardening
step that can land in a 1.x release without a surface change.

## Consequences

- The surface is committed. From 1.0, changes to the items above are
  semver-significant: additive until 2.0.
- The correctly-rounded claim the surface makes is backed by the
  per-function rounding-status table (published in README and docs by
  pf-ud3g), the five-mode differential lanes (bit-exact against MPFR,
  ADR-0038), and the per-release cross-check sweep (ADR-0049). The
  f32-exhaustive oracle certifies NearestEven for all functions and all
  five modes for 51 of the 63 status rows; the remaining 12 have their
  directed modes certified by the differential lanes and the cross-check
  sweep rather than the f32 bridge, which carries NearestEven only. The
  status table reports this honestly per function; this ADR does not
  restate it.
- `ziv_instrumented` consumers (the cross-check harness) take no
  stability promise; that is by design.
